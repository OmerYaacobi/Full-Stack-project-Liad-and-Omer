# אבטחה בסיסית — PayrollPortal

כלל שאנחנו מחזיקים: **אם כל שורת TypeScript בריפו תוחלף בחיבור Postgres עם JWT תקף של עובד, העובד עדיין לא יקרא משכורת של מישהו אחר.**

פירוט מדיניות: [technical-design/02-rls.md](technical-design/02-rls.md).
למה תפקיד אסור ב-`user_metadata`: [for-liad-role-security.md](for-liad-role-security.md).

---

## 1. Authentication — איך מתבצע

- **ספק:** Supabase Auth. אדם אחד = שורת `auth.users` + שורת `profiles` (trigger `handle_new_user`).
- **שיטות:** סיסמה (הרשמת משרד והזמנה), או magic link. אותה סכימת אימייל ב-Zod (trim + lowercase).
- **סשן:** עוגיות HTTP דרך `@supabase/ssr`. `proxy.ts` קורא `updateSession` בכל בקשה שאינה נכס סטטי, כדי לרענן את ה-JWT לפני שפג.
- **מזהה לבדיקות הרשאה:** רק `auth.uid()` החתום ב-JWT. לא אימייל מהלקוח, לא header שאנחנו ממציאים.

שני מסלולי הרשמה, בכוונה לא סימטריים:

| מסלול | מה נוצר | מה **לא** קורה |
| --- | --- | --- |
| `/signup/bookkeeper` | firm חדש + חברות בפירמה | לא ניתן "לבחור" להיות משרד בתוך עסק קיים |
| `/invite/[token]` | membership עם `invitations.role` | המשתמש לא בוחר employee/manager; הטוקן קובע |

`DEV_AUTH_ROLE` קיים רק ל-UI מקומי, בלי קידומת `NEXT_PUBLIC_`, ומתעלמים ממנו ב-`NODE_ENV=production`. הוא לא עוקף RLS: השאילתות עדיין אנונימיות ומחזירות ריק.

## 2. Authorization — איך מתבצע

ארבע שכבות. הראשונות הן UX; האחרונה היא גבול.

1. **`proxy.ts`** — בלי סשן, כל נתיב לא-ציבורי → `/login`. לא יודע תפקיד (אין DB כאן).
2. **`requireRole` ב-layout** — מנהל לא רואה shell של משרד; מופנה ל-`roleHome`. זה לא אבטחה מול תוקף שמזמן Action ישירות.
3. **Server Action** — אחרי Zod, קורא את הלקוח עם JWT. נכשל مبחור עם הודעה קריאה. לא מחליף RLS.
4. **Postgres RLS + RPCs** — מדיניות על כל טבלת tenant. `anon` כמעט בלי גישה (חריג: קריאת הזמנה לפי טוקן כדי להציג שם עסק). `service_role` **לא בשימוש**.

עוזרי SQL ב-schema `app`, `security definer`, עם `search_path` קבוע:

- `app.has_role(company, roles)` — membership פעיל
- `app.my_employee_id(s)` — רשומות HR של הלוגין
- `app.can_decide_time_off` — מנהל או משרד באותו עסק, **לא** המבקש עצמו

`(select auth.uid())` כדי ש-Postgres יחשב uid פעם אחת ל-statement.

תפקיד **לא** נקרא מ-`user_metadata`. המשתמש יכול להריץ `updateUser({ data: { role: "bookkeeper" } })` עם ה-anon key — זו קריאה לגיטימית. אם מדיניות הייתה קוראת משם, כל עובד היה מקדם את עצמו. התפקיד חי ב-`memberships.role` / `firm_memberships`, ונכתב רק בידי מי שכבר מורשה (הזמנה, trigger, משרד).

## 3. פעולות שמותרות רק למשתמש מחובר

ציבורי בלי סשן: `/`, `/login`, `/signup/*`, `/verify`, `/invite/*`, `/auth/*`.

כל השאר דורש סשן, ואז תפקיד:

| פעולה | מי |
| --- | --- |
| לראות תלוש / יתרה / לבקש חופשה / להעלות 101 | עובד או מנהל של אותו עסק |
| לאשר חופשה, לראות צוות, לוח שנה, קבצים משותפים | מנהל (או משרד לאישור) |
| להעלות תלוש, לפרסם חודש, ליצור עסק, להזמין, terminate | משרד בלבד |
| להוריד קובץ | מחובר **וגם** מעבר של SELECT על שורת המטא-דאטה, ואז signed URL |

פעולות "רק מחובר" בלי תפקיד עדיין נחסמות ב-RLS: משתמש מחובר בלי membership מגיע ל-`/no-access` ולא מקבל שורות tenant.

## 4. איך מונעים גישה למידע של משתמש אחר

| סיכון | הגנה |
| --- | --- |
| עובד A קורא תלוש של B | SELECT על `payslips`: שורה של עצמו ו-`published`, או מנהל עם `visible_to_managers`, או משרד של **אותו** `company_id` |
| ניחוש UUID ב-URL (`/api/payslips/[id]`) | Route Handler קורא `getPayslipOpenUrl` שדורש שה-SELECT יצליח; אחרת אין 307 |
| מנהל פותח PDF שלא שותף | מדיניות Storage + דגל per-file; `file_path` בטבלה אינו היתר הורדה |
| משרד של לקוח X קורא לקוח Y | `companies.firm_id` + `firm_memberships`; אין SELECT חוצה פירמות |
| הצצה לטיוטה | עובד/מנהל לא רואים `draft` / `unassigned` |
| הרצת Action עם `employeeId` של אחר בבקשת חופשה | השרת גוזר employee מהסשן; הלקוח לא שולח את המזהה |
| עדכון סטטוס חופשה ב-UPDATE ישיר | `revoke update, delete`; רק `decide_time_off` / `cancel_time_off` |
| צירוף עצמי לצוות / שינוי `manager_id` | אין UPDATE לעובד; RPC עם בודק תפקיד |
| הרשמה לעסק בלי הזמנה | אין יצירת membership מהקליינט; רק trigger עם טוקן חי |
| קובץ ציבורי | באקטים `public = false`; קישורים מתים אחרי ~120 שניות |
| מנהל רואה את כל הילדים בעץ | `manages_employee` הוא hop אחד בכוונה. נראות חופשה רחבה יותר (כל מנהלי העסק) — מתועדת, לא "admin" |

שיתוף עם מנהלים הוא **לפי קובץ**, לא "המנהל רואה הכל". ברירת המחדל בהעלאה חדשה דלוקה; אפשר לכבות.

## 5. ולידציה לקלטים

שלוש שכבות. הדפדפן נחשב עביר.

1. HTML / disable כפתור (יתרה, סוג קובץ).
2. Zod ב-Action לפני כל כתיבה: טיפוסים, טווחים, MIME, גודל, ת.ז., אימייל, אורך סיבה, נטו ≤ ברוטו, טווח חופשה ≤ 90 ימים.
3. אילוצי Postgres: enums, CHECK על גודל קובץ 1–10MB, UNIQUE, EXCLUDE לחפיפה, RPCs שדוחים סטטוס לא-pending.

העלאות: magic bytes `%PDF` לתלוש, רשימת MIME למסמכים, תקרת 10MB גם בבאקט Storage (נדחה לפני האפליקציה אם עוברים). לא סומכים על `workingDays` מהלקוח.

XSS: React בורח טקסט. לא מזריקים HTML מסיבת החופשה. אין `dangerouslySetInnerHTML` על קלט משתמש.

SQL injection: PostgREST / פרמטרים, לא מחרוזות SQL באפליקציה.

## 6. הגנה על קריאות API

אין REST פתוח של CRUD. המשטח:

| משטח | הגנה |
| --- | --- |
| Server Actions | POST של Next (Origin של האתר), סשן בעוגייה, Zod, RLS |
| `/api/payslips/[id]` ודומיו | GET אחרי בדיקת שורה; 307 ל-URL חתום, לא streaming של הקובץ דרך השרת כ-proxy ארוך |
| `/api/payslips/parse` | סשן משרד; גוף multipart; לא נשמר בלי הקצאה |
| `/auth/callback` | מחליף `code` בסשן; לא מקבל טוקן מה-query שאנחנו ממציאים |
| PostgREST הישיר | אפשרי טכנית עם anon key (הוא ציבורי). **RLS חייב להחזיק.** זה תרחיש ה-threat הראשי, ולכן המדיניות נכתבה כאילו אין Next.js |

אין rate limit ייעודי באפליקציה (קוד `RATE_LIMITED` שמור ב-`ErrorCode` אבל לא מחובר). נשענים על מגבלות Supabase/Vercel. העלאה: מקסימום 30 PDF לקבוצה.

CSRF: Server Actions בודקים origin. עוגיות Auth הן לפי הגדרת Supabase SSR (לא משותפות לסקריפט צד-שלישי לגיטימי).

## 7. שמירת סודות ו-API keys

| מפתח | איפה | למה |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | `.env.local`, Vercel env | חייב `NEXT_PUBLIC_` כדי שהדפדפן יקבל אותו |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | אותו דבר | **מיועד להיות ציבורי.** בלי RLS הוא חסר ערך; עם RLS הוא הזהות של המשתמש |
| `service_role` | **לא בפרויקט** | עוקף RLS. כל `NEXT_PUBLIC_*` נארז ל-JS שהמבקר מוריד — לשים אותו שם = גישת DB מלאה לכל מבקר |
| `DEV_AUTH_ROLE` | רק `.env.local`, בלי `NEXT_PUBLIC_` | ignored ב-production |

`.env.local` ב-gitignore. `.env.example` מסביר במפורש לא להוסיף `service_role`.

אין מפתחות של רשות המסים, סליקה, או SMTP באפליקציה. פענוח PDF לא קורא לשירות חיצוני.

Signed URL לקובץ הוא סוד קצר-חיים: מי שהשיג אותו בחלון של ~שתי דקות יכול להוריד; אחרי זה לא. לא שולחים אותו במייל.

## 8. סיכונים שנשארו ומה היינו משפרים

| סיכון | חומרה | מצב | שיפור |
| --- | --- | --- | --- |
| קישור הצטרפות רב-פעמי שדלף | גבוה | מי שמחזיק את קישור **המנהל** מצטרף כמנהל | תפוגה קצרה יותר, סיבוב תכוף, הזמנה לפי אימייל כברירת מחדל |
| אין אימות אימייל מחמיר בכל סביבה | בינוני | תלוי בהגדרת Supabase | Confirm email חובה ב-production |
| סיסמה מינימום 6 תווים | נמוך–בינוני | Zod | מדיניות חזקה יותר + Have I Been Pwned |
| אין 2FA | בינוני | לא ממומש | TOTP למשרד (גישה לכל הלקוחות) |
| אין rate limit על login / parse | בינוני | קוד מוכן, לא מחובר | הגבלה ב-proxy או ב-Supabase |
| PDF זדוני בפענוח | בינוני | קבצים מגיעים מהמשרד | sandbox / timeout / ספרייה מבודדת |
| URL חתום ששותף בצ'אט בתוך 120 שניות | נמוך | TTL קצר | TTL קצר יותר, או stream דרך השרת |
| אין אוטומציית RLS tests בריפו | גבוה לתחזוקה | ידני | CI עם JWT לכל תפקיד נגד המקרים ב-A3–A11 |
| UI באנגלית, ת.ז. ומסמכים רגישים | פרטיות | מינימום נתונים; ת.ז. לשידוך | הצפנה בעמודה / שמירת last4 בלבד בהמשך |
| `audit_log` נראה למשרד בלבד, אין SIEM | נמוך ב-v1 | RPCs כותבים | ייצוא / התראות על terminate ו-publish |
| תלות ב-Supabase כ-boundary | ארכיטקטוני | מקובל לקורס | אם ניפרד: אותו מודל RLS ב-Postgres עצמאי |
| אין CSP / headers מחמירים בקוד | נמוך | ברירת Vercel | `headers` ב-next.config: CSP, HSTS |
| מנהל רואה חופשות של כל העסק | מוצרי | מכוון (0006) | אם יידרש: חזרה ל-line-manager בלבד לתלושים, לא לחופשה |

מה לא נסגור ב-v1 במכוון: אנחנו לא מחשבים שכר, אז אין מסלול "לשנות נטו אחרי publish" בלי נעילת תקופה. תקופה `locked` אמורה למנוע שינוי שקט של מספר שהעובד כבר ראה.

## 9. סיכום לשאלה "מה עשיתם כדי שיהיה מאובטח"

- זהות ב-Supabase Auth; תפקיד בטבלה שלנו, לא ב-metadata.
- RLS על כל טבלת tenant; אין `service_role` באפליקציה.
- מכונות מצבים ב-RPC, לא UPDATE מהלקוח.
- קבצים פרטיים + URL קצר-חיים אחרי בדיקת שורה.
- Zod + אילוצי DB; ימי חופשה ומזהה עובד מחושבים בשרת.
- הזמנה לפי תפקיד; עובד לא יכול להירשם כמנהל דרך קישור העובד.
