# תכנון ארכיטקטורת התוכנה — PayrollPortal

מסמך זה מתאר **איך המערכת בנויה**, ברמה של רכיבים וזרימת מידע.  
פירוט טבלאות, הרשאות וקוד נמצא ב-[technical-design/](technical-design/).

שמות קבועים במסמכים: **עובד**, **מנהל**, **משרד**.  
«עסק» = חברת לקוח אחת. «פירמה» = משרד הנהלת החשבונות שמנהל כמה עסקים.

---

## 1. הרכיבים

```
דפדפן  →  Next.js ב-Vercel  →  Supabase
              │                    │
              │ קריאת דפים         │ Auth (התחברות)
              │ כתיבה מטפסים       │ Postgres (נתונים + הרשאות)
              │ הורדת קבצים        │ Storage (PDF-ים פרטיים)
```

| רכיב | בשביל מה |
| --- | --- |
| Next.js (App Router) | האתר, הניתוב, והלוגיקה בשרת |
| TypeScript | טיפוסים בכל הקוד |
| Supabase Auth | התחברות בסיסמה או בקישור למייל |
| Supabase Postgres | כל הנתונים. ההרשאות חיות במסד (RLS) |
| Supabase Storage | קבצים פרטיים: תלושים, מסמכים, אישורי מחלה |
| Vercel | אירוח האתר (דרישת הקורס) |
| Zod | בדיקת קלט לפני כל כתיבה |
| pdf-parse / pdf2json | פענוח תלוש **בשרת**, לא בדפדפן |

**RLS** = Row Level Security: כלל במסד שאומר אילו שורות כל משתמש מחובר רשאי לראות.  
החלטה מרכזית: גם אם מישהו יעקוף את האתר וידבר ישר עם המסד, עם הזהות של עובד הוא עדיין לא יקרא משכורת של מישהו אחר.

אין API ציבורי של Create/Read/Update/Delete. הדפדפן לא מושך משכורות ב-JavaScript. הקריאות עוברות דרך השרת, עם הזהות של המשתמש המחובר. מפתח-על של Supabase (`service_role`) **לא נמצא בפרויקט**.

## 2. מסד הנתונים

כן — Postgres ב-Supabase. הסכימה ב-`supabase/migrations/` (קבצים 0001 עד 0012).

הישויות העיקריות, בעברית:

| בעברית | טבלה | מה שומרים |
| --- | --- | --- |
| פרופיל | `profiles` | אדם אחד לכל חשבון התחברות |
| פירמה / חברות בפירמה | `bookkeeping_firms`, `firm_memberships` | המשרד והאנשים שלו |
| עסק | `companies` | לקוח אחד של המשרד |
| חברות בעסק | `memberships` | התפקיד בעסק: עובד או מנהל. **כאן חי התפקיד** |
| הזמנה | `invitations` | קישור הצטרפות (רב-פעמי או חד-פעמי) |
| רשומת עובד | `employees` | כרטיס HR. יכול להתקיים גם לפני שהאדם נרשם |
| חודש שכר | `payroll_periods` | טיוטה / פורסם / נעול |
| תלוש | `payslips` | תלוש אחד לעובד בחודש |
| חופשה | `leave_types`, `leave_entitlements`, `time_off_requests` | סוגים, מכסות, בקשות |
| מסמכים | `documents` | 106, 101, חוזה, פנסיה, אחר |
| צירוף לצוות | `team_join_requests` | מנהל מבקש, עובד מאשר |
| חגים | `company_holidays` | לחישוב ימי עבודה |
| יומן פעולות | `audit_log` | נכתב רק מתוך פונקציות במסד |

סיכומי שכר ויתרות חופשה **לא** מחושבים ב-SQL. האתר מחשב אותם ב-TypeScript, על שורות שהמסד כבר סינן לפי הרשאה.

## 3. העמודים

כל אזור תפקיד בודק שהמשתמש באמת בתפקיד הזה. מנהל יכול גם להיכנס לאזור העובד (השכר האישי שלו).

| אזור | מה יש שם |
| --- | --- |
| ציבורי | דף בית, כניסה, הרשמת משרד, הזמנה, אימות מייל, תנאי שימוש, פרטיות |
| עובד | דשבורד, תלושים, מסמכים, טופס 101, חופשה |
| מנהל | סקירת צוות, אישורים, אנשי צוות, קבצים משותפים, לוח שנה |
| משרד | מה דורש טיפול, אישורים, עסקים, חודשי שכר, מסמכים |

בכל בקשה לאתר, `proxy.ts` מרענן את הסשן. מי שלא מחובר מופנה לכניסה.  
ה-proxy **לא** מחליט תפקיד — לזה צריך את המסד.

---

## 4. איך האתר מדבר עם המסד

שלושה סוגים, לפי הצורך:

1. **קריאת דף** — השרת טוען נתונים ומרנדר HTML (תלושים, יתרות, תורים).
2. **Server Action** — כתיבה מטופס: יצירת עסק, בקשת חופשה, פרסום חודש, העלאת קובץ.
3. **Route Handler** — כשצריך HTTP אמיתי: סיום התחברות, יציאה, הורדת קובץ, פענוח PDF.

פונקציות במסד (RPC) משמשות רק לשינוי סטטוס שחייב להיות אטומי, למשל: אישור חופשה, פרסום חודש, צירוף לצוות, סיום העסקה. ככה שני אנשים לא יכולים לאשר את אותה בקשה בשנייה.

רשימת הפעולות לפי קובץ: [03-api.md](technical-design/03-api.md).

## 5. זרימת מידע

**עובד פותח את הדשבורד**

1. הדפדפן מבקש את העמוד.
2. הסשן מתרענן.
3. השרת בודק שהמשתמש עובד או מנהל.
4. השאילתה למסד רצה **בתור המשתמש המחובר**. המסד מחזיר רק שורות שמותרות לו.
5. הסיכומים מחושבים בשרת. המספרים מגיעים ב-HTML. הדפדפן לא מושך משכורות בנפרד.

**עובד שולח בקשת חופשה**

1. הטופס נשלח לשרת.
2. הקלט נבדק. אם לא תקין — הודעה ליד השדה, בלי כתיבה.
3. השרת מחשב בעצמו מי העובד וכמה ימי עבודה (לא סומך על מה שהדפדפן שלח).
4. נוצרת בקשה במצב «ממתין». המסד חוסם חפיפה עם חופשה אחרת.
5. הדף מתרענן.

**הורדת קובץ**

השרת בודק שהמשתמש רשאי לראות את השורה במסד, ורק אז נותן קישור זמני לקובץ (בערך שתי דקות).

התחברות ויציאה הן הפעולות היחידות שרצות בדפדפן מול Supabase, כי שם צריך לכתוב עוגייה.

## 6. הרשאות

התפקיד שמור בטבלה שלנו, לא בפרופיל שהמשתמש יכול לשנות בעצמו בדפדפן. לכן עובד לא יכול «להפוך למשרד» מקונסול.

| יכולת | עובד | מנהל | משרד |
| --- | :---: | :---: | :---: |
| השכר והתלושים של עצמו | כן | כן | לא (לא על מצבת הלקוח) |
| בקשת חופשה / ביטול בהמתנה | כן | כן | לא |
| העלאת טופס 101 | כן | כן | לא |
| רשימת אנשי העסק | לא | כן | כן |
| תלוש של עובד אחר | לא | רק אם שותף | כן |
| אישור חופשה (לא של עצמו) | לא | כן, כל העסק | כן, כל לקוח של הפירמה |
| לבקש צירוף לצוות | לא | כן (העובד מאשר) | שיוך ישיר |
| העלאת תלושים / פרסום חודש | לא | לא | כן |
| יצירת עסק, הזמנות, סיום העסקה | לא | לא | כן |

ארבע שכבות, מהקלה לחזקה:

1. בלי סשן אין כניסה לאזור הפרטי.
2. עמוד של תפקיד אחר מפנה הביתה (נוחות, לא חומה מול תוקף).
3. השרת בודק לפני כתיבה ומחזיר הודעה ברורה.
4. המסד הוא הגבול האמיתי.

## 7. למה בחרנו את הספריות האלה

| בחירה | למה |
| --- | --- |
| Next.js | קריאת שכר בשרת כברירת מחדל, בלי לכתוב API ידני לכל פעולה |
| TypeScript | אותם טיפוסים באתר ובשרת |
| Supabase + RLS | ההרשאה במסד, לא רק בקוד האתר |
| Supabase Auth | אותה זהות שהמסד בודק |
| Storage פרטי | קובץ לא ציבורי; הורדה רק בקישור זמני |
| Tailwind | עיצוב בלי ספריית רכיבים חיצונית |
| Zod | אותם כללי קלט בטופס ובשרת |
| תאריכים כטקסט `YYYY-MM-DD` | יום לוח לא זז בגלל אזור זמן |
| פענוח PDF בשרת | התלוש לא עובר פענוח אצל העובד |
| Vercel | דרישת הקורס, מתאים ל-Next.js |

מה לא שילבנו בכוונה: Redux (הנתונים מגיעים עם הדף), ספריית טבלאות, התראות קופצות, ספריית גרפים כבדה, מפתח-על של המסד, וריצה לילית לצבירת ימי חופשה.
