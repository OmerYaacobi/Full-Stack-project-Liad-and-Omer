# מסמך אפיון בדיקות — PayrollPortal

מטרת המסמך: להגדיר מה זה אומר שהמוצר "עובד" — לא לכסות כל שורת קוד.
חובה לבדוק את התהליכים המרכזיים, הרשאות בין תפקידים, קלטים לא תקינים, ומסד הנתונים.

שיטות מתוכננות:

| שכבה | כלי | מה בודקים |
| --- | --- | --- |
| יחידה (אוטומטי) | Node Test Runner (`npm test`) על `tests/` | ימי עבודה בישראל, סופ״ש וחגים, תובנות שכר, ולידציות Zod, שידוך עובד |
| הרשאות | מקרי RLS / SQL כ-JWT של כל תפקיד | עובד א׳ לא קורא את ב׳; מנהל רואה רק עסק משותף |
| תהליך עסקי | בדיקה ידנית מתועדת | הזמנה → העלאה מרובה → פרסום → בקשת חופשה → אישור |
| UI | בדיקה ידנית לפי תפקיד | empty states, שגיאות שדה, ניווט, תצוגות מקדימות |

קוד הבדיקות האוטומטיות נמצא תחת `tests/` ומורץ בלחיצה אחת עם `npm test`. [05-test-report.md](05-test-report.md) מתעד ביצוע מלא של כלל הבדיקות.

שלושה משתמשי עזר לכל סבב: עובד A, עובד B (או מנהל), מנהל חשבונות של אותו עסק. רצוי גם מנהל חשבונות של עסק אחר (tenant isolation).

## 3. בדיקות לתהליכים עסקיים מקצה לקצה

אלה התהליכים שחייבים לעבוד בהדגמה.

**E1 — משרד מפרסם חודש, עובד רואה תובנות**

משרד יוצר עסק → מזמין עובד → העובד נרשם → המשרד פותח תקופה, מעלה תלוש, מקצה, מפרסם → העובד רואה סכומים בדשבורד וב-`/employee/payslips` → לפני הפרסום העובד ראה empty state.

**E2 — בקשת חופשה עד אישור**

עובד מבקש 3 ימי עבודה → מופיע אצל המנהל עם אזהרת חפיפה אם רלוונטי → מנהל מאשר → יתרה יורדת → לוח שנה ירוק. מסלול חלופי: משרד מאשר כשאין מנהל קו.

**E3 — צירוף לצוות בהסכמה**

מנהל מבקש → העובד מאשר → המנהל רואה נטו אחרון ב-`/manager/team`. בלי אישור הרשימה לא משתנה.

**E4 — סיום העסקה בלי לאבד היסטוריה**

משרד terminate → העובד לא נכנס לסביבת העסק → התלושים שפורסמו נשארים במסד עבור המשרד.

## 4. בדיקות הרשאות

הכשלון שהמוצר לא יכול להרשות: עובד קורא משכורת של אחר.

| מזהה | ניסיון | תוצאה צפויה |
| --- | --- | --- |
| A1 | אנונימי ל-`/employee` | הפניה ל-`/login` |
| A2 | עובד ל-`/bookkeeper` | הפניה ל-`/employee` (requireRole) |
| A3 | עובד A קורא `payslips` של B (שאילתה ישירה / ניחוש id) | אפס שורות / 42501, לא את הסכום |
| A4 | עובד A פותח `/api/payslips/{id-של-B}` | אין URL חתום |
| A5 | עובד מעלה תלוש / מפרסם תקופה | forbidden |
| A6 | עובד מאשר את הבקשה של עצמו | RPC מסרב |
| A7 | עובד מאשר בקשה של אחר | forbidden |
| A8 | מנהל רואה PDF של אחר כש-`visible_to_managers = false` | לא |
| A9 | מנהל רואה כשהדגל דלוק | כן, רק published |
| A10 | עובד רואה תלוש draft | לא |
| A11 | משרד של עסק X קורא תלושים של עסק Y | לא |
| A12 | שינוי `user_metadata.role` ל-bookkeeper | RLS ו-`memberships` לא משתנים; אין גישת משרד |
| A13 | הצטרפות בלי טוקן / עם טוקן פג | אין membership |
| A14 | מנהל מוחק עסק / terminate | forbidden |
| A15 | קריאת `audit_log` כעובד | לא |

Storage: אובייקט בנתיב של עובד אחר לא נפתח גם אם יודעים את ה-path. URL חתום שפג (אחרי ~120 שניות) נכשל.

## 5. בדיקות למסד הנתונים

| מזהה | אילוץ | איך |
| --- | --- | --- |
| D1 | RLS דלוק על טבלאות tenant | `relrowsecurity` ב-catalog |
| D2 | `anon` בלי מדיניות — אין SELECT על `payslips` | JWT אנונימי |
| D3 | UNIQUE `(period_id, employee_id)` | INSERT כפול → 23505 |
| D4 | EXCLUDE חפיפת חופשה | בקשה חופפת pending/approved → 23P01 |
| D5 | unscheduled לא משתתף ב-EXCLUDE | שתי בקשות: אחת dated ואחת unscheduled באותם תאריכים דמה — מותר לפי האפיון |
| D6 | עובד INSERT ל-`documents` עם kind ≠ form_101 | נדחה |
| D7 | אין UPDATE/DELETE ישיר על `time_off_requests` | revoke; שינוי סטטוס רק ב-RPC |
| D8 | `publish_payroll_period` אטומי | אחרי הצלחה גם התקופה וגם התלושים published |
| D9 | `decide_time_off` פעמיים | השני P0001 / already decided |
| D10 | `handle_new_user` מעתיק role מההזמנה, לא מ-metadata | הרשמה עם metadata מזויף עדיין נכנסת כעובד |

אינדקסים קיימים (לא חובה לבדוק בכל סבב, כן לוודא אחרי מיגרציה): `idx_payslips_employee_period`, `idx_time_off_company_pending`, `idx_memberships_profile_active`, ועוד — ראו מסמך הסקייל.

## 8. הגדרת "עובד" לסבב הגשה

המוצר נחשב עובד להגשה אם:

1. שלושת התפקידים נכנסים ורואים רק את הניווט שלהם.
2. E1–E3 עוברים (פרסום שכר, חופשה, צוות).
3. A3, A5, A6, A11 עוברים (אין דליפת שכר, אין כתיבת שכר לעובד, אין אישור עצמי, אין חציית tenant).
4. קלטים V4–V9 נדחים בלי 500.
5. empty states ב-U2/U7 ברורים.

לא חובה: כיסוי 100%, E2E על כל מסך, בדיקות עומס, נגישות WCAG מלאה.
