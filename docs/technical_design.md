מסמך זה מתאר את ארכיטקטורת התוכנה של המערכת, התכנון הטכני המפורט, זרימת המידע, מבנה בסיס הנתונים וההחלטות הטכנולוגיות המרכזיות.

---

## 1. ארכיטקטורת המערכת והרכיבים
המערכת בנויה בארכיטקטורת שרת-לקוח מודרנית מבוססת ענן, תוך שימוש ב-React Server Components.

```text
[ Client / Browser ]  <--->  [ Next.js on Vercel ]  <--->  [ Supabase ]
   (React / UI)              (App Router / Server)         (Postgres DB + RLS)
                                                           (Auth Services)
                                                           (Storage Buckets)
```

**רכיבים טכנולוגיים מרכזיים ומטרתם:**
* **Next.js (App Router):** משמש כ-Full-Stack Framework. אחראי על הניתוב, רינדור צד-שרת (SSR), ולוגיקת השרת (API & Server Actions). נבחר כדי לפשט את זרימת המידע בין השרת ללקוח.
* **TypeScript:** מספק Type-Safety מלא (End-to-End), מהמסד (דרך טיפוסי Supabase) ועד לקומפוננטות הקצה.
* **Supabase Auth:** ניהול זהויות מאובטח (Authentication) מבוסס JWT. תומך בהתחברות באמצעות סיסמה או קישור למייל (Magic Link).
* **Supabase Postgres:** מסד הנתונים הרלוציוני. מכיל את כלל הישויות וכן את לוגיקת ההרשאות (Row Level Security - RLS).
* **Supabase Storage:** אחסון קבצים פרטי (Object Storage) המחולק ל-Buckets ייעודיים (`payslips`, `documents`, `time_off`). הגישה לקבצים מתבצעת רק דרך Signed URLs.
* **Zod:** ספריית סכמות לביצוע ולידציות מחמירות על קלטים בצד השרת ובצד הלקוח.
* **Vercel:** פלטפורמת הענן לאירוח האפליקציה (Frontend & Serverless Functions), המותאמת באופן אופטימלי ל-Next.js.

## 2. מבנה בסיס הנתונים (Database Schema)
מסד הנתונים מנוהל ב-PostgreSQL. סכמת הנתונים והמיגרציות מנוהלות בתיקיית `supabase/migrations/`.

**הישויות והטבלאות המרכזיות:**
* **`profiles`**: פרופיל אישי לכל משתמש מאומת (מקושר ישירות ל-Supabase Auth).
* **`bookkeeping_firms` & `firm_memberships`**: ייצוג משרד הנהלת החשבונות וצוות העובדים שלו (Bookkeepers).
* **`companies`**: ייצוג העסקים (הלקוחות) המנוהלים על ידי משרדי הנהלת החשבונות.
* **`memberships`**: טבלת הקישור המרכזית המגדירה את התפקיד (`employee` או `manager`) של משתמש בתוך עסק ספציפי.
* **`employees`**: כרטיס ה-HR הבסיסי של העובד בעסק. ישות זו יכולה להיות קיימת גם טרם הרשמת העובד בפועל למערכת.
* **`payroll_periods`**: חודשי השכר. מנהל סטטוסים (`draft`, `published`, `locked`) לשליטה בחשיפת המידע.
* **`payslips`**: תלושי השכר החודשיים. מקושרים לעובד ולחודש שכר ספציפי.
* **`time_off_requests` & `leave_entitlements`**: ניהול מאגר ימי החופשה, סוגי חופשות, ובקשות ממתינות/מאושרות.
* **`documents`**: רשומות המצביעות לקבצים ב-Storage (`form_106`, `form_101`, `contract` ועוד).
* **`invitations` & `team_join_requests`**: ניהול תהליכי צירוף משתמשים והזמנות מאובטחות (לפי תפקיד).

*הערה ארכיטקטונית:* חישובים כמו סיכומי שכר ויתרות חופשה **לא** נשמרים כמידע סטטי במסד (כדי למנוע חוסר סנכרון), אלא מחושבים דינמית בצד השרת בעת הבקשה, בהתבסס על הנתונים הגולמיים המאושרים.

## 3. מבנה תיקיות וקומפוננטות מרכזיות
הפרויקט בנוי בסטנדרט של Next.js App Router:

* **`src/app/`**: מכיל את הראוטינג (Pages & Layouts). מחולק לתיקיות לפי הרשאות: `(auth)/`, `(employee)/`, `(manager)/`, `(bookkeeper)/`.
* **`src/components/`**: קומפוננטות UI לשימוש חוזר (UI Components).
  * `ui/`: רכיבים טיפשים (Dumb components) כגון כפתורים, מודלים, וטפסים (מעוצבים ב-Tailwind CSS).
  * `features/`: קומפוננטות חכמות המקושרות ללוגיקה (למשל: `PayslipUploader`, `TimeOffCalendar`).
* **`src/lib/`**: לוגיקה עסקית ותשתיות:
  * `actions/`: קובצי Server Actions (פעולות CRUD מאובטחות).
  * `utils/`: פונקציות עזר וחישובים (כמו חישוב ימי עבודה ללא סופ"ש).
  * `validations/`: סכמות Zod לולידציה.
* **`src/supabase/`**: הגדרות החיבור למסד הנתונים וניהול הסשנים (Clients עבור Browser ו-Server).

## 4. זרימת מידע ו-API (CRUD Operations)
המערכת אינה חושפת REST API ציבורי סטנדרטי (למעט חריגים בודדים), אלא מסתמכת על המנגנונים הבאים:

1. **קריאת נתונים (Read):** מתבצעת ישירות מתוך ה-React Server Components. השרת מושך נתונים מה-DB עם ההרשאה של המשתמש המחובר, מבצע חישובים (Aggregation) ומרנדר HTML. הדפדפן אינו פונה ישירות למסד הנתונים.
2. **כתיבת נתונים (Create, Update, Delete):** מתבצעת באמצעות **Server Actions**. פונקציות אלו נקראות ישירות מהטפסים בקליינט. לדוגמה: יצירת לקוח (`company`), הגשת בקשת חופשה, אישור חופשה, העלאת קבצים או עדכון סטטוס חודש שכר.
3. **Route Handlers:** משמשים לפעולות HTTP ייעודיות שאינן מתאימות ל-Server Actions, כגון: `/auth/callback` (לאימות משתמש), Webhooks, ו-Endpoints לחילול Signed URLs מאובטחים להורדת קבצי PDF.

**ניהול קונפליקטים (Concurrency):** פעולות קריטיות (כמו אישור חופשה מתוך תור ממתינים) מתבצעות דרך פונקציות פנימיות ב-Postgres (RPC) כדי להבטיח פעולות אטומיות (ACID) ולמנוע מצב שבו שני מנהלים מאשרים את אותה בקשה באותה שנייה.

## 5. State, ולידציות, שגיאות וחוויית משתמש (UX)
* **ניהול State באפליקציה:** המערכת נמנעת משימוש בספריות State מורכבות (כמו Redux). ה-Server State מנוהל על ידי Next.js (דרך Fetch Cache ו-Server Components). ה-Client State מצומצם למינימום (פתיחת מודלים, טפסים מקומיים) ומנוהל על ידי React `useState`.
* **ולידציות קלטים:** כל קלט מהמשתמש, ללא יוצא מן הכלל, עובר ולידציה כפולה. תחילה בצד הלקוח (לפידבק מיידי), ולאחר מכן בצד השרת בתוך ה-Server Action באמצעות סכמות של Zod. בקשה שאינה תואמת לסכמה נדחית מידית לפני כל פנייה למסד הנתונים.
* **טיפול בשגיאות (Error Handling):** המערכת משתמשת ב-`error.tsx` ברמת ה-App Router כדי לתפוס שגיאות שרת. שגיאות לוגיות (למשל, חוסר הרשאה, יתרה לא מספקת לחופשה) מוחזרות למשתמש בצורה ידידותית ומוצגות כ-Toast Notifications או הודעות שגיאה inline בתוך הטופס.
* **תכנון UX מרכזי:** המערכת תוכננה להיות מהירה (Zero Layout Shift תודות ל-SSR), נגישה, וברורה. משתמש ללא הרשאה המנסה לגשת לנתיב שגוי לא יראה דף שגיאה טכני, אלא יופנה באלגנטיות לדף הבית הרלוונטי לתפקידו.

## 6. הרשאות ואבטחה (Authorization & RLS)
התפקיד של המשתמש שמור בטבלאות מערכת עמוקות (`memberships`) ולא ב-Profile, כדי למנוע מניפולציה מצד הקליינט. מודל האבטחה בנוי בגישת "Defense in Depth" (4 שכבות):

1. **Routing:** ללא Session תקף, הניתוב חסום ברמת ה-Middleware.
2. **UI/UX:** עמוד השייך לתפקיד אחר מפנה מידית לדף הבית (הפרדה לוגית: `/employee`, `/manager`, `/bookkeeper`).
3. **Server Validation:** ה-Server Actions מוודאים את תפקיד המשתמש מול המסד לפני ביצוע כל פעולת כתיבה.
4. **Row Level Security (RLS) ב-Postgres:** זהו קו ההגנה המוחלט. הגישה לטבלאות מותנית בחוקים ברמת השורה. לדוגמה: משתמש המוגדר כ-`employee` יקבל מהמסד אך ורק שורות מטבלת `payslips` המשויכות ל-ID שלו ושסטטוס ה-`payroll_period` שלהן הוא `published`. גם ניסיון עקיפה באמצעות API חיצוני ייכשל ברמת המסד. המערכת אינה משתמשת ב-`service_role` (מפתח על) בקליינט.
