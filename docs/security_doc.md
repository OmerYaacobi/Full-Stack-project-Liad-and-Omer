# מסמך אבטחה בסיסית (Security Architecture) — PayrollPortal

**תרגיל סיום, Internet Technologies, RUNI CS 2026**
**מגישים:** ליעד פילוסוף ועומר יעקבי

עקרון העל המנחה את ארכיטקטורת האבטחה של המערכת הוא **Zero Trust כלפי הקליינט**: לעולם אין לסמוך על הלקוח (הדפדפן). גם במידה ומשתמש מסוג `employee` עוקף את ממשק המשתמש (UI) ופונה ישירות ל-API או למסד הנתונים באמצעות האסימון (Token) שלו, המערכת תחסום גישה למידע שאינו שייך לו [cite: 1].

## 1. מנגנוני אימות והרשאות (Authentication & Authorization)

### אימות זהויות (Authentication)
ההתחברות מתבצעת דרך שירותי Supabase Auth המבוססים על JWT (JSON Web Tokens). המערכת תומכת בשני נתיבי אימות [cite: 1]:
* כניסה באמצעות אימייל וסיסמה (מיועד בעיקר לרישום משרד רואי החשבון והצטרפות מהזמנות).
* כניסה באמצעות קישור קסם (Magic Link) למייל.
הסשן (Session) המאומת נשמר ב-Cookie מאובטח ומתרענן בכל פנייה לשרת באמצעות Middleware (`proxy.ts`). זהות המשתמש מול מסד הנתונים נקבעת אך ורק על פי פונקציית `auth.uid()` המאומתת, ולא על פי נתונים שהדפדפן שולח.

### ניהול הרשאות (Authorization)
מודל ההרשאות מבוסס על Role-Based Access Control (RBAC), אך התפקיד (`employee`, `manager`, `bookkeeper`) **אינו** נשמר בשדה נגיש לעריכה כמו `user_metadata` בפרופיל המשתמש [cite: 1]. התפקיד מעוגן בטבלאות מערכת סגורות (`memberships` / `firm_memberships`) ונכתב אך ורק בתהליך הזמנה מאובטח (Invitations) או על ידי בעל הרשאת מנהל חשבונות. משתמש אינו יכול "לשדרג" את עצמו לתפקיד אחר.

**פעולות המותרות רק למשתמש מחובר [cite: 1]:**
* ללא התחברות, הגישה מוגבלת לדפים הציבוריים בלבד (`/login`, `/signup`, תנאי שימוש, וקבלת הזמנה). ניסיון גישה לאזור אישי יגרור הפניה מיידית החוצה.
* **`employee` / `manager`:** צפייה בתלושים אישיים (שפורסמו בלבד), הגשת בקשות חופשה, והעלאת טופס 101.
* **`manager`:** אישור/דחיית חופשות של עובדים (לא של עצמו), צפייה בלוח שנה צוותי, וגישה למסמכים שתויגו בפירוש כ-`visible_to_managers`.
* **`bookkeeper`:** העלאת תלושים, פרסום חודשי שכר (`publish_payroll_period`), יצירת עסקים תחת ניהולו, ניהול הזמנות לעובדים, וסיום העסקת עובדים (`terminate_employee`).

## 2. בידוד נתונים והגנה על פרטיות (Data Isolation)

ההגנה על המידע ומניעת חשיפת נתונים של משתמש אחד למשנהו [cite: 1] מתבצעת בגישת Defense in Depth (הגנה רב-שכבתית), כאשר השכבה הקריטית ביותר היא מסד הנתונים:

* **Row Level Security (RLS):** כל טבלאות הלקוח ב-Postgres מוגנות ב-RLS. חוקי ה-RLS מוודאים ברמת השורה את זכות הגישה. לדוגמה: משתמש א' לא יקבל רשומות שכר של משתמש ב', גם אם ישלח בקשת קריאה עוקפת. ה-RLS יסנן אוטומטית ויחזיר מערך ריק או שגיאת הרשאה.
* **הפרדת ארגונים (Multi-Tenancy Isolation):** משתמשי ה-`bookkeeper` משויכים ל-`bookkeeping_firm`. ה-RLS מונע ממנהל חשבונות של משרד א' לקרוא או לערוך נתונים של עסק (`company`) השייך למשרד ב'.
* **גישה לקבצים מסווגים (Storage Security):** קבצים נשמרים ב-Buckets פרטיים לחלוטין. ניסיון לנחש URL או לשתף קישור הורדה ייכשל. הורדת קובץ מתבצעת רק לאחר שהשרת מוודא הרשאה במסד, ורק אז מחולל Signed URL המוגבל בזמן קצר (120 שניות).
* **פעולות אטומיות ו-State Machines:** אי אפשר לשנות סטטוסים קריטיים (כמו אישור חופשה) באמצעות שאילתת `UPDATE` רגילה מהקליינט. הפעולה מחייבת שימוש בפונקציית RPC סגורה (`decide_time_off`) המוודאת הרשאות ותקינות תהליכית.

## 3. הגנה על ממשקי השרת וולידציות קלט (API Protection & Validation)

### ולידציית קלטים (Input Validation)
כל נתון המוזן למערכת עובר 3 שכבות של ולידציה לאימות תקינות ומניעת חדירות [cite: 1]:
1. **צד לקוח (UI):** משוב מיידי המונע פעולות שגויות בסיסיות (כגון חסימת כפתור להגשת חופשה החורגת מהיתרה).
2. **צד שרת (Zod ב-Server Actions):** כל קריאה לשרת עוברת דרך סכמת Zod נוקשה המוודאת מבנה מייל, חוקיות ת.ז. (7-9 ספרות), הגבלות גודל (עד 10MB לקובץ, מקסימום 30 קבצים), בדיקות לוגיות (תאריך סיום גדול מתאריך התחלה), ווידוא היגיון פיננסי (שכר נטו אינו יכול לעלות על הברוטו).
3. **רמת מסד הנתונים (DB Constraints):** אכיפה סופית באמצעות Constraints (כגון מניעת הזנת סטטוס שאינו מורשה), אינדקסים ייחודיים (למניעת העלאה כפולה של תלוש), ואילוצי Exclusion (למניעת תאריכי חופשות חופפים). בנוסף, נעשה שימוש בשאילתות מקונפגות (Parameterized Queries) למניעת SQL Injection.

### הגנה על קריאות API
המערכת אינה פותחת Endpoints של REST API לביצוע CRUD גנרי. התקשורת מתבצעת באמצעות Server Actions מאובטחים [cite: 1]. פעולות ייעודיות הדורשות API Route (כמו הורדת קבצים או Webhooks לאימות) נבדקות מול ה-Session הפעיל וה-RLS לפני כל פעולה.

## 4. ניהול סודות וסיכונים עתידיים (Secrets & Future Risks)

### ניהול סודות ומפתחות מזהים (Secrets Management)
* **אסימוני פיתוח לעומת ייצור:** מפתח ה-`NEXT_PUBLIC_SUPABASE_ANON_KEY` נועד להיות חשוף לקליינט. הגישה לנתונים אינה מבוססת עליו אלא על חוקי ה-RLS. 
* **הימנעות מ-Service Role:** פרויקט זה **אינו** משתמש במפתח `service_role` (העוקף הגנות RLS). החלטה ארכיטקטונית זו מונעת סכנה של השתלטות עוינת על המסד עקב דלף מפתח [cite: 1].
* **הפרדת סביבות:** משתני הסביבה (Environment Variables) כגון `DEV_AUTH_ROLE` (המאפשר מעקף התחברות לצורכי פיתוח) מנוהלים בקובץ `.env.local` שאינו עולה למאגר הקוד (Git) ומנוטרל לחלוטין בסביבת הייצור (Vercel).

### סיכוני אבטחה שטרם כוסו (Future Security Improvements)
כדי לעמוד בתקני אבטחה מחמירים יותר בעתיד (במיוחד עבור מידע פיננסי), נדרשות ההשלמות הבאות [cite: 1]:
1. **הגנת Rate Limiting:** כרגע אין מנגנון אקטיבי להגבלת קצב הבקשות במסכי ההתחברות (מניעת Brute Force) או למנגנון פענוח ה-PDF (מניעת התקפת חסימת שירות - DoS).
2. **אימות דו-שלבי (2FA/MFA):** משתמשי `bookkeeper` מחזיקים בגישה למידע רגיש של מאות עובדים ממספר חברות. חובה ליישם מנגנון 2FA לכניסתם.
3. **אורך חיי קישורים (Token Expiration):** קישורי הצטרפות למנהלים עלולים לדלוף ולשמש גורמים זרים להצטרפות לצוות הניהול. יש לקצר את משך חייהם או לדרוש אישור שניוני מטעם ה-`bookkeeper` בטרם ההצטרפות בפועל.
4. **בדיקות אבטחה אוטומטיות:** כיום ה-RLS נבדק ידנית. יש להוסיף חבילת בדיקות E2E ענפה המדמה תקיפות גישה למסד הנתונים בכל פריסה (CI/CD pipeline).
