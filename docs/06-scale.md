# סקייל בסיסי — PayrollPortal

המוצר מכוון לעשרות עד מאות משתמשים פעילים: משרד אחד עם כמה עסקי SMB, בכל עסק עשרות עובדים, כמה מנהלים. זה לא מוצר למיליוני משתמשים אנונימיים. המסמך מסביר מה קורה בסקאלה הזו, מה כבר מגן עלינו, ומה יישבר קודם.

---

## 1. מה יקרה עם עשרות או מאות משתמשים

| שכבה | התנהגות בסקאלה הזו |
| --- | --- |
| Vercel | כל בקשת דף היא Server Component קצר-חיים. עשרות משתמשים במקביל נכנסים ל-serverless רגיל בלי שינוי בקוד. |
| Supabase Auth | סשן בעוגייה; `proxy.ts` מרענן בלי לרוץ על static assets. |
| Postgres | רוב השאילתות הן "התלושים שלי" / "הממתינים בעסק" — מאות שורות, לא מיליונים. RLS מוסיף `auth.uid()` לכל שאילתה; עם אינדקסים על `profile_id` / `company_id` זה נשאר index lookup. |
| Storage | PDF-ים פרטיים. צוואר הבקבוק הוא העלאה מרובה (פענוח CPU), לא מספר הקוראים. |
| Next.js | נתוני שכר לא נשלפים ב-waterfall מצד הלקוח. דף אחד = כמה שאילתות בשרת ב-render אחד. |

צווארי בקבוק ריאליים **לפני** "מאות משתמשים":

1. משרד מעלה 30 תלושים ומפענח PDF ב-request אחד (CPU + זמן).
2. מנהל פותח לוח שנה לחודש עם הרבה בקשות — היום בלי pagination.
3. משרד עם הרבה לקוחות פותח `/bookkeeper/documents` — כל הקבצים של הפירמה בבת אחת.

מאות עובדים שנכנסים לראות את התלוש שלהם **לא** אמורים להפיל את המערכת: כל אחד קורא כמה שורות עם `employee_id` ממנוכס.

## 2. שאילתות שעלולות להיות כבדות

| שאילתה | למה היא כבדה | מתי זה כואב |
| --- | --- | --- |
| תור אישורי חופשה של המשרד (`listFirmPendingApprovals`) | כל ה-`pending` בכל הלקוחות | פירמה עם עשרות עסקים וחופשות קיץ |
| לוח שנה (`listManagerCalendar`) | כל הבקשות ה-dated בחודש לכל העסק | עסק גדול, חודש אוגוסט |
| רשימת אנשים + נטו אחרון לצוות | join תלושים לכל דיווח ישיר | מנהל עם עשרות דיווחים |
| ארון מסמכים של הפירמה (`listFirmDocuments`) | כל המסמכים של כל הלקוחות | שנים של 106/חוזים |
| חיפוש עובד להקצאת תלוש | `pg_trgm` על `full_name` | עדיין סביר למאות שמות; לא למיליון |
| פענוח PDF | לא SQL — CPU ב-Route Handler | 30 קבצים × עמודים סרוקים |
| `buildPayInsights` | בזיכרון על חודשים שפורסמו | זניח: לכל היותר עשרות חודשים לעובד |
| יתרות חופשה | entitlements + כל הבקשות של העובד, סיכום ב-TS | עובד ותיק עם שנים של בקשות — עדיין קטן |

מה **לא** כבד בכוונה: דשבורד העובד (כמה תלושים אחרונים + יתרות של עצמו). RLS חותך קודם, ואז TypeScript מחשב.

אין Views של `v_salary_stats` שנסורקים לכל החברה בכל רענון. זה היה עלול להפוך ל-seq scan על כל התלושים.

## 3. אינדקסים

קיימים במיגרציות, בעיקר ב-0001:

| אינדקס | על | למה |
| --- | --- | --- |
| `idx_memberships_profile_active` | `(profile_id) WHERE is_active` | כל request: "מי אני" |
| `idx_memberships_company_role` | `(company_id, role) WHERE is_active` | `app.has_role` |
| `idx_firm_memberships_profile` / `_firm` | profile / firm, פעילים | כניסת משרד |
| `idx_companies_firm` | `firm_id` | רשימת לקוחות |
| `idx_employees_company_status` | `(company_id, status)` | רשימת מצבה |
| `idx_employees_national_id` | `(company_id, national_id)` | שידוך תלוש |
| `idx_employees_manager` | `manager_id` | צוות ישיר |
| `idx_employees_name_trgm` | GIN על `full_name` | חיפוש הקצאה |
| `idx_payslips_employee_period` | `(employee_id, period_id)` | דשבורד + ייחודיות |
| `idx_payslips_unassigned` | `(company_id, status) WHERE unassigned` | תור הקצאה |
| `idx_time_off_employee_status` | `(employee_id, status)` | יתרות |
| `idx_time_off_company_pending` | `(company_id, status) WHERE pending` | תור אישורים |
| `idx_time_off_dates` | `(start_date, end_date)` | לוח שנה / חפיפה |
| `idx_documents_lookup` | `(employee_id, kind, tax_year)` | תיקיות |
| `idx_invitations_token` | `token` | דף הזמנה |
| `idx_audit_log_company` | `(company_id, created_at desc)` | לוג משרד |
| `idx_team_join_employee_pending` | pending pair | בקשות צוות |
| GIST exclude על בקשות חופשה | טווח תאריכים | חפיפה ב-O(log n) במקום נעילה שגויה |

`btree_gist` נדרש ל-EXCLUDE. בלי האינדקסים האלה מדיניות RLS על `memberships` הייתה seq scan לכל שורה ב-`payslips`.

## 4. איך נמנעים מטעינה מיותרת

- **Server Components כברירת מחדל.** משכורות לא נכנסות ל-JS bundle ולא נמשכות ב-`useEffect`.
- **Select ממוקד.** לא `select('*')` לדשבורד — רק העמודות שמוצגות (סכומים, סטטוס, חודש).
- **תובנות בשרת.** `buildPayInsights` מקבל מערך קטן שכבר סונן ל-published.
- **`React.cache` על `getContext`.** כמה layouts באותו render לא שואלים Auth שלוש פעמים.
- **`proxy.ts` matcher** מדלג על `_next/static` ותמונות — בלי round-trip ל-Supabase לכל אייקון.
- **URL חתום לקובץ.** הדפדפן מוריד מ-Storage רק אחרי לחיצה, לא ב-render של הרשימה.
- **גרף SVG מנתונים מוכנים.** אין ספריית charts שמושכת את כל ההיסטוריה בצד הלקוח.
- **אין polling / realtime.** המנהל רואה בקשות חדשות ברענון דף. זה חוסך חיבורים; המחיר הוא UX בלי התראות.

מה עדיין נטען יותר מדי: רשימות בלי תקרת שורות (מסמכי פירמה, תלושי עובד לכל השנים, תור הפירמה).

## 5. Pagination

**אין pagination ב-UI היום.** ההנחה: עובד רואה עשרות תלושים לכל היותר; תור אישורים הוא עשרות, לא אלפים.

| מסך | מצב נוכחי | מה צריך בגרסה הבאה |
| --- | --- | --- |
| תלושי עובד | כל ה-published | `limit` + "טען עוד" אחרי ~24 חודשים |
| תור אישורים | כל ה-pending | מספיק עכשיו; cursor לפי `created_at` אם יגדל |
| ארון מסמכי פירמה | הכל | סינון לפי עסק/kind + עמודים |
| רשימת עסקים | הכל | סביר למשרד קטן |
| לוח שנה | חודש אחד (`?month=`) | זה כבר חיתוך לפי זמן — כן שימוש נכון בגבול |
| העלאה מרובה | מקסימום 30 | תקרת batch במקום דף |

`?month=YYYY-MM` בלוח השנה הוא הגבול היחיד שממומש כמו pagination לפי מפתח. חודש ב-URL הוא cacheable וניתן לשיתוף.

קובצי Storage: אין "טעינת כל ה-PDF". הרשימה היא מטא-דאטה; הבינארי רק בלחיצה.

## 6. הפרדה בין צד לקוח לצד שרת

| עבודה | איפה | למה |
| --- | --- | --- |
| קריאת שכר, יתרות, תורים | שרת (RSC) | לא לחשוף שורות ב-network tab של ה-JS |
| ולידציה + כתיבה | שרת (Action) | הלקוח עביר |
| חישוב ימי עבודה / תובנות | שרת (וגם preview בשרת) | אותו מספר ב-insert |
| פענוח PDF | שרת בלבד | ספריות Node; לא לשלוח parser לעובד |
| שיוך תפקיד | Postgres trigger | לא מהדפדפן |
| מכונת מצבים | RPC עם `FOR UPDATE` | שני קליקים במקביל |
| כניסה/יציאה | לקוח (`client.ts`) | חייב לכתוב עוגייה |
| מצב טופס, דיאלוג, בחירת יום | לקוח | אין סיבה ל-round trip |
| `DEV_AUTH_ROLE` | שרת, לא `NEXT_PUBLIC_` | לא מגיע לדפדפן |

הפרדה שגויה הייתה: `createBrowserClient` לכל ה-CRUD. אז RLS עדיין היה רץ, אבל הסכומים היו ב-XHR גלוי, והיינו צריכים לנהל loading/error בכל מסך. בחרנו RSC כדי שהפרדה תהיה ברירת מחדל.

## 7. מגבלות במוצר הנוכחי

1. **אין pagination** על רשימות ארוכות.
2. **פענוח PDF סינכרוני** ב-request — 30 קבצים כבדים עלולים לפגוע ב-timeout של Vercel (כ-10–60 שניות לפי תוכנית).
3. **אין תור רקע / cron.** אין צבירת חופשה לילית, אין שליחת מייל, אין עיבוד PDF אסינכרוני.
4. **RLS לכל שאילתה** עולה ב-CPU של Postgres לעומת `service_role` + בדיקה באפליקציה. בסקאלה שלנו זה מחיר נכון; בסקאלה ענקית היו מאחדים reads ל-views מאובטחות.
5. **`getContext`** טוען memberships + firm בכל ניווט. עם הרבה חברויות (נדיר אצלנו) זה מתרחב.
6. **משרד אחד = כל הלקוחות בזיכרון הדף** בארון המסמכים ובתור.
7. **אין CDN לקבצים פרטיים** מעבר ל-signed URL של Supabase — מתאים לפרטיות, פחות לסטרימינג המוני.
8. **חישוב יתרות ב-TypeScript** במקום view מחולשת. נכון לעשרות בקשות; לא ליומן נוכחות יומי לכל עובד.
9. **אין caching HTTP** של דפי שכר (נכון — פרטיים). כל כניסה לדשבורד הולכת ל-DB.
10. **Connection pooling** הוא של Supabase. אנחנו לא מנהלים pool בעצמנו; serverless פותח חיבורים קצרים דרך ה-anon key + JWT.

## 8. מה היינו משפרים לסקאלה גדולה יותר

| עדיפות | שיפור | למה |
| --- | --- | --- |
| 1 | Pagination + סינון בארון המסמכים ובתור הפירמה | זה יישבר ראשון אצל משרד אמיתי |
| 2 | עיבוד PDF בתור (Supabase Queue / Vercel background) | מנתק את העלאה מזמן ה-HTTP |
| 3 | מטריאליזציה של יתרת חופשה (עמודה מעודכנת מ-trigger) | אם יהיו אלפי בקשות לעובד |
| 4 | `limit` על תלושי עובד + ארכיון לפי שנה | דשבורד נשאר קל אחרי 10 שנים |
| 5 | Cache קצר של `getContext` (cookie / JWT claims שאנחנו חותמים, לא metadata של המשתמש) | פחות קריאות membership בכל layout — בלי לשים `role` ב-user_metadata |
| 6 | קריאת לוח שנה כטווח אינדקס בלבד (`start_date <= monthEnd AND end_date >= monthStart`) | כבר יש אינדקס תאריכים; לוודא שהשאילתה משתמשת בו |
| 7 | Observability: זמני שאילתה, timeout בפענוח | לדעת מה כבד לפני שהמשתמש מתלונן |
| 8 | Read replica / רק אם יש דיווחי משרד כבדים | מוקדם מדי ל-v1 |
| 9 | מיילים אסינכרוניים | מוריד רענוני דף; דורש תור |

עקרון: **לא לבטל RLS בשביל מהירות.** אם צריך reads כבדים למשרד, נבנה RPC `security definer` מצומצם שרץ אחרי בדיקת `firm_memberships`, לא נפתח את הטבלה.

לסיכום: הסקאלה הנוכחית (עשרות–מאות) נשענת על אינדקסים לפי tenant, קריאות צרות בשרת, ותקרת batch לקבצים. החור הגדול הוא רשימות בלי עמודים ופענוח סינכרוני — שניהם ידועים ומתוכננים לגרסה הבאה.
