## 1. מבנה התיקיות בפרויקט
הפרויקט בנוי בסטנדרט של Next.js App Router. אין שימוש בספריית רכיבים חיצונית שלמה (כמו shadcn), והטיפוסים כתובים ידנית ב-`types/app.ts` (ללא מחולל טיפוסים אוטומטי מהמסד).

```text
app/                         # App Router pages and layouts
  (auth)/                    # login, signup, invite
  (employee)/                # employee dashboard, payslips, time-off
  (manager)/                 # manager views, approvals, team
  (bookkeeper)/              # bookkeeping firm views, queue, clients
  api/                       # Route handlers (file download, PDF parse)
components/                  # UI components
  ui/                        # Dumb components (buttons, dialogs)
  features/                  # Domain-specific components (e.g., payslips, time-off)
lib/                         # Business logic and server utils
  actions/                   # Server Actions (form submissions, mutations)
  domain/                    # Domain logic (working days math, pay insights)
  payslip/                   # PDF parser and employee-matching logic
  validations/               # Zod schemas for input validation
  supabase/                  # Supabase clients (server / browser)
proxy.ts                     # Middleware / Session refresher
supabase/migrations/         # SQL Schema + RLS rules (0001–0012)
tests/                       # Unit and integration tests (`npm test`)
types/                       # TypeScript types (`app.ts` for roles and models)
docs/                        # Project documentation (PRD, Architecture, etc.)
```

## 2. מבנה הקומפוננטות המרכזיות
ארכיטקטורת ה-UI מתבססת על **React Server Components** כברירת מחדל, כדי לחסוך שליחת JavaScript מיותר לדפדפן ולאפשר שליפת נתונים מאובטחת.
השימוש ב-`"use client"` מוגבל אך ורק לקומפוננטות הדורשות אינטראקציה (טפסים, לוח שנה, העלאת קבצים מרובה). 

לדוגמה, בדשבורד של ה-`employee`:
* **Server Components:** שליפת סיכומי השכר, יתרות החופשה ורשימת התלושים האחרונים מבוצעת בצד השרת.
* **Client Components:** כרטיס `IncomingTeamJoinList` (אישור/דחיית צירוף לצוות) וגרף מגמת השכר רצים בדפדפן, אך מוזנים בנתונים (Props) שכבר חושבו בשרת.

התפריט הצדדי דינמי לחלוטין ונגזר מתפקיד המשתמש (Role). לדוגמה, `employee` לא רואה בתפריט פריטים של `manager`, ו-`bookkeeper` כלל אינו רואה אזור שכר אישי.

## 3. מבנה בסיס הנתונים (Database Schema)
העקרונות המנחים לתכנון הסכמה (פירוט מלא במיגרציות 0001-0012):
* **הפרדת ישויות (Auth vs HR):** קיימת הפרדה בין חשבון ההתחברות (`profiles`) לבין כרטיס העובד (`employees`). הפרדה זו מאפשרת ל-`bookkeeper` להעלות תלושים לעובד עוד בטרם נרשם למערכת.
* **ניהול תפקידים:** התפקיד (Role) אינו נשמר בפרופיל המשתמש, אלא בטבלאות קשר (`memberships` / `firm_memberships`). התפקיד מועתק מטבלת ה-`invitations` בעת ההרשמה, והמשתמש אינו יכול לשנותו בעצמו.
* **ניהול סטטוסים למחיקה (Soft Delete):** עובדים אינם נמחקים לחלוטין (Hard delete). במקום זאת, השדה `employees.status` הופך ל-`terminated`. בדומה, בקשת חופשה מקבלת סטטוס `cancelled`.
* **טיפוסי נתונים וייחודיות:** נתוני שכר נשמרים כ-`numeric`. תאריכים נשמרים כ-`date` (ובאפליקציה מטופלים כמחרוזת `YYYY-MM-DD` למניעת בעיות אזור זמן). מוגדר אילוץ Unique על הצמד `(period_id, employee_id)` למניעת כפילות תלושים. מנגנון `file_checksum` מונע העלאה כפולה של אותו PDF.

## 4. פעולות CREATE/READ/UPDATE/DELETE (CRUD) מרכזיות
ההרשאות נגזרות קשיחות ברמת ה-RLS (Row Level Security). ככלל, משתמשים כמעט ולא מבצעים מחיקה פיזית. 

| ישות / טבלה | מי יוצר (CREATE) | מי קורא (READ) | מי מעדכן (UPDATE) | מי מוחק (DELETE) |
| :--- | :--- | :--- | :--- | :--- |
| **`employees`** | הזמנה או `bookkeeper` | העובד עצמו, מנהלי העסק, `bookkeeper` | `bookkeeper` + פונקציות RPC של צוותים | אין (רק העברה ל-`terminated`) |
| **`payslips`** | `bookkeeper` | העובד עצמו (אחרי `published`), מנהל (אם `visible_to_managers`), `bookkeeper` (תמיד) | `bookkeeper` (עד לסטטוס `locked`) | מחיקה רק כשהסטטוס `unassigned` |
| **`time_off_requests`** | עובד (במצב `pending`) | העובד, מנהליו, `bookkeeper` | רק דרך פונקציות RPC (`decide`, `cancel`) | אין (רק העברה ל-`cancelled`) |
| **`documents`** | `bookkeeper` (עובד רשאי להעלות רק `form_101`) | העובד, מנהל (אם תויג כ-`visible`), `bookkeeper` | `bookkeeper` (ניהול שדות חשיפה) | `bookkeeper` |
| **`payroll_periods`** | `bookkeeper` | כל חברי העסק | `bookkeeper` | `bookkeeper` (רק אם החודש ריק מתלושים) |

## 5. תיאור ה-API והלוגיקה העסקית המרכזית

### תיאור ה-API
המערכת משתמשת ב-**Server Actions** עבור כתיבה (Mutations). אין API פתוח ל-CRUD. ה-Actions אינם זורקים שגיאות קריסה לדפדפן; הם מחזירים אובייקט תוצאה הכולל את הנתונים במקרה של הצלחה, או הודעת שגיאה ברורה וידידותית במקרה של כישלון (כגון שגיאות ולידציה או חוסר הרשאה). ה-Auth נשען על Cookie Sessions וזהות המשתמש מועברת ל-RLS בכל קריאה. **אין שימוש במפתח Service Role** שעוקף הרשאות.

### תיאור הלוגיקה העסקית המרכזית
* **סיכומי שכר (Insights):** מחושבים בשרת רק על חודשי שכר שסטטוסם `published`. ממוצע 12 חודשים מוצג רק במידה וישנם 3 חודשים מפורסמים לפחות (למניעת הטיה). 
* **חישוב ימי עבודה:** מתבצע תוך ספירת שני קצוות התאריכים. סופי שבוע (שישי-שבת) אינם נספרים. חגים מוגדרים במסד: חג מלא אינו נספר, וערב חג נספר כחצי יום. למרות שהדפדפן מציג תצוגה מקדימה לחישוב, שמירת הבקשה מחשבת את הימים **מחדש בשרת**.
* **ניהול יתרות חופשה:** אין צבירה אוטומטית כרונית (Cron). היתרה מחושבת דינמית כנוסחה: `(מכסה + יתרה מועברת + התאמות) פחות (ימים שאושרו + ימים בהמתנה)`. בקשה בהמתנה גורעת ימים באופן מיידי כדי למנוע יתרת-חסר. רק ה-`bookkeeper` רשאי לעדכן התאמות ביתרה לפי תלוש השכר.
* **תהליכי סטטוסים (State Machines פנימיים):** למשל בניהול תלושים: `unassigned` -> `assigned` -> `published`. במעבר ל-`published` לא ניתן לחזור אחורה, ורק אז התלוש נחשף.
* **שידוך תלושים והגנת פרטיות:** ה-Parser רץ בשרת ומציע לעובד מתאים, אך **לעולם** אינו משייך קובץ אוטומטית ללא אישור אנושי, למניעת זליגת מידע פיננסי אישי.
* **פונקציות RPC:** עדכוני סטטוס קריטיים (כמו אישור חופשה) מבוצעים דרך פונקציות מסד (RPC) כדי למנוע קונפליקטים (Concurrency).

## 6. State באפליקציה וטיפול בשגיאות

### ניהול ה-State (מצב)
המערכת דוגלת בגישת Server-First ואינה משתמשת בספריות ניהול State גלובליות כמו Redux.
* **Server State:** התלושים, בקשות החופשה והיתרות נטענים ישירות מהשרת בעת טעינת הדף. לאחר ביצוע פעולת כתיבה (לדוגמה, אישור חופשה), ה-Route עובר רענון מחדש (Revalidation) והנתונים המעודכנים מושכים מהשרת (אין Optimistic Updates לפעולות קריטיות כגון אישורים).
* **URL State:** סינון חודשים בלוח השנה מתבצע דרך ה-URL (למשל `?month=2026-08`), מה שמאפשר שיתוף לינקים ומעבר טבעי בין דפים.
* **Local / Component State:** משמש לניהול שדות טפסים, חיוויי טעינה ("שולח..."), מצב דיאלוגים ופתיחת כרטיסיות.
* מצב ההתחברות (מי מחובר) מנוהל אך ורק באמצעות Cookies.

### טיפול בשגיאות
לכל אזור תפקיד מוגדרים קבצי `error.tsx` ו-`loading.tsx`.
* במקרה של קלט שגוי: המשתמש מקבל הודעת שגיאה מקומית בסמוך לשדה הרלוונטי.
* חוסר הרשאה: הצגת הודעה מפורשת "אין לך הרשאה לעשות את זה", ללא חשיפת שגיאות שרת.
* התנגשות לוגית (למשל אישור חופשה שכבר אושרה על ידי מנהל אחר): המערכת מציגה הודעה שהבקשה כבר טופלה, ומרעננת את הרשימה באופן יזום.
* מצב "חסר נתונים": העדפה להצגת מסך ריק (Empty State) הכולל הסבר והנחיות לצעד הבא (למשל, "התלוש יופיע לאחר שהמשרד יפרסם את החודש").

## 7. ולידציות של קלטים
מערכת הוולידציה בנויה מ-3 שכבות הגנה (לפי עקרון ה-Zero Trust כלפי הקליינט):
1. **ולידציית Client-side (דפדפן):** מניעת קלט שגוי בסיסי (כגון חסימת כפתור של בקשת חופשה במידה והכמות עולה על היתרה).
2. **ולידציית Server-side (באמצעות Zod):** כל Server Action בודק את הקלט מול סכמה קשיחה טרם הפנייה למסד. בדיקות אלו כוללות תקינות מייל, אורך סיסמה, מבנה ת.ז. (7-9 ספרות), אימות תאריכים לוגי (תאריך סיום גדול מתאריך התחלה), הגבלת גודל קבצי PDF (עד 10MB ועד 30 קבצים), ווידוא היגיון פיננסי (נטו אינו גדול מברוטו). יתרה מכך, השרת **לא** סומך על הדפדפן בנוגע לספירת ימי חופשה, ומבצע את ספירת הימים מחדש.
3. **ולידציית Database-side (ב-Postgres):** אכיפה סופית דרך אילוצים (Constraints), Unique Keys, ו-Exclusion (למניעת חפיפת תאריכי חופשות).

## 8. תכנון חוויית המשתמש המרכזית (UX)
עיצוב חוויית המשתמש ממוקד בתכליתיות. כל דף בית (Dashboard) נפתח תוך מענה על "שאלת הליבה" של התפקיד, ללא צורך בניווט נוסף:
* **Employee:** "כמה הרווחתי ומה היתרה שלי?" -> תצוגת כרטיסי סיכום, יתרת חופשה וגישה מהירה לתלושים האחרונים.
* **Manager:** "מי מחכה לאישור שלי ומי חסר בצוות?" -> תצוגת בקשות ממתינות, תור המשימות, ולוח שנה מרוכז לחופשות הצוות.
* **Bookkeeper:** "מהו צוואר הבקבוק כרגע?" -> תצוגת חודשי שכר שטרם פורסמו וחופשות חריגות הממתינות לאישור.

התפריט הראשי מסתיר נתיבים חסומים. פעולות קריטיות (הסרת עובד, מחיקת עסק, פרסום שכר) דורשות מנגנון "אישור כפול" למניעת שגיאות אנוש.
