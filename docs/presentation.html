PayrollPortal

A payroll portal for bookkeeping firms and their client businesses

Liad Pilosof and Omer Yaacobi

Next.js · TypeScript · Supabase · Vercel

~45 seconds. Name, who we are, what it is. No demo yet — start with the problem.
The problem

Payroll is already calculated. Sharing it is not.

  • An employee asks for a pay slip or Form 106 on WhatsApp — the firm sends PDFs one by one.
  • A manager approves vacation in a spreadsheet, with no leave balance and no view of who else is away.
  • Nobody can answer “how much was deducted from me this year?” without opening a pile of files.
  • A firm that manages several clients keeps separate folders, with no clear permission split.

We do not replace the payroll engine. We replace the email chain.

~1 minute. Out of scope: gross-to-net. In scope: each person sees only what they are allowed to see.
Users and customer

The customer is the firm. Three roles inside it.

The firm

A bookkeeping practice. It brings several businesses, uploads pay slips, and invites staff.

Employee and manager

End users. A manager is also an employee: personal pay, plus a team.

One company at a time

An employee sees only their company. The firm sees its own clients, not another firm’s.

~45 seconds. Customer = the bookkeeping firm. Users = employee, manager, bookkeeper.
Business value

Why this saves time

  • Firm — upload many slips at once, suggest a match by ID number, publish a month in one click.
  • Employee — pay slip, leave balance, and Form 101 without messaging the firm.
  • Manager — an approval queue with balances, and a calendar of who is away.
  • Everyone — drafts stay hidden. A manager sees another person’s file only if it is shared. Role comes from the invite.
~1 minute. Each line is something we actually built, not a slogan.
The product

Three screens, one app

Employee

Pay summary, leave balances, slips, documents, time-off request, Form 101, accept a team-join ask.

Manager

The same personal area, plus approvals, team by consent, shared files, and a calendar.

Bookkeeper

Several businesses, draft then publish a month, PDF parse, documents, and leave approval when no manager is there.

If time allows: a short demo — publish a month as the firm, then show what the employee sees. Otherwise demo at the end.
Architecture

The app runs on the server. Permissions live in the database.

BrowserUI
→
Next.js on VercelPages and form writes
→
SupabaseAuth, data, files
  • Payroll is loaded on the server with the page — not by JavaScript in the browser.
  • Form writes are checked on the server. There is no public table API.
  • Leave approval and month publish run as database functions, so two clicks cannot overwrite each other.
  • Files are private. A download link expires after about two minutes.
  • There is no superuser key in the app. The database decides what each user sees.
~90 seconds. Line to remember: even without our website, an employee using their own login still cannot read someone else’s salary.
Database

Each company has its own data. Role lives in our table.

AreaWhat we store
Who signs inA profile, membership in a company, membership in a firm
PayrollA month and a pay slip. One slip per employee per month
LeaveEntitlements and requests. The database blocks overlapping days
FilesDocuments filed to one person. Sharing with managers is per file
TeamA manager asks, the employee accepts

Role comes from the invite. The user cannot change it in their profile in the browser.

~1 minute. If they ask how it connects: firm → companies → employees → pay slips and leave.
Core flows

Three things that have to work

1. Publish a month

Draft, upload PDFs, the system suggests an employee, a person confirms, then publish. Before that, the employee sees an empty state.

2. Time off

The server counts working days. A pending request uses the balance. A manager or the firm decides. You cannot approve your own request.

3. Join a team

A manager asks, the employee accepts. The firm can assign a line manager directly. Removing from a team is not termination.

~90 seconds. If time remains, show one of these three on screen.
Tests

What “it works” means

  • Flows: publish a month, time off through approval, join a team — checked by hand.
  • Permissions: an employee cannot see another’s pay, write payroll, approve themselves, or cross companies.
  • Bad input: net above gross, a non-PDF file, leave over the balance — rejected without a crash.
  • Math: working days, pay summaries, and input rules run in npm test (22 tests).

Still missing: automated browser tests, and automated permission tests against the database.

~45 seconds. Be honest: unit tests exist; the main flows and permissions were manual.
Scale

Tens to hundreds of users, not millions

What holds at this size

Indexes by company and employee. Payroll loads on the server. At most 30 PDFs per upload. The calendar is one month at a time.

What breaks first

The firm-wide document cabinet with no pages. Heavy PDF parsing in the same request as the upload.

An employee opening their own slip reads a few of their rows. That is not the load. The load is the firm uploading and listing everything at once.

~1 minute. Do not say “we are ready for a million.” Say where the real limit is.
Security

Four layers. The real boundary is the database.

  1. With no session, the private app is closed.
  2. The wrong role’s page sends you home (convenience).
  3. The server checks input before any write.
  4. The database — even without our website, an employee cannot see someone else’s salary.

Role lives in our table, not in a field the user can edit. Files are private. No superuser key in the app.

Still open: a leaked manager invite link, no two-factor for the firm, no rate limit on login.

~90 seconds. If they ask one question: why role is not in user-editablex profile metadata. That is the strong story.
